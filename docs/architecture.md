# 架构与设计决策

> 状态：有效
>
> 本文描述旦食后端当前架构、持久化约束和服务层协议。数据库对象的精确定义以 `migrations/*.sql` 为准，HTTP wire contract 以生成的 `api/openapi.json` 为准。

## 1. 目标与原则

旦食后端是一个以 PostgreSQL 为一致性核心的 Go HTTP 服务。设计目标是：

1. 用明确的分层和单一事务边界承载业务逻辑；
2. 把引用完整性、机械派生和不可篡改性落实为数据库约束；
3. 把只有业务上下文才能判断的语义留在 service 层；
4. 让 schema、HTTP 契约和错误码都有可执行的单一真源；
5. 让服务在配置错误或 schema 版本错误时拒绝启动，而不是带病运行；
6. 使用真实 PostgreSQL 验证关键行为，不以 mock 替代数据库语义。

核心分界是：

- 数据库负责外键、唯一性、状态形态、机械计数、追加不可篡改和禁止物理删除；
- service 负责事务内编排、权限、版本连续性、跨表发布条件、锁顺序和外部副作用；
- handler 只处理 HTTP 输入输出，不承载持久化逻辑。

## 2. 技术决策总览

| 领域 | 决定 | 理由 |
|---|---|---|
| HTTP | Hertz，手写路由分组 | 路由结构直接可读，避免引入与 JSON API 无关的 IDL 生成代码 |
| ORM | GORM 2 + pgx 5 | 复用 GORM 的查询和模型能力，同时使用 pgx PostgreSQL 驱动 |
| Schema | goose SQL migrations | 数据库约束复杂，SQL 才能完整表达；不使用 AutoMigrate |
| 数据库 | PostgreSQL 18 | 使用现代约束、索引和查询能力；本地与 CI 统一版本 |
| 主键 | `bigint GENERATED BY DEFAULT AS IDENTITY` | 8 字节索引、连接与排序成本低；`BY DEFAULT` 支持受控 ETL 显式装载 |
| 金额 | `NUMERIC(10,2)` + `decimal.Decimal` + JSON string | 全链路不经过二进制浮点数 |
| 配置 | Viper 显式 `BindEnv`，随后反序列化到值对象 | 环境变量清单可审计，业务代码不读取全局配置单例 |
| 认证 | HS256 JWT + `user_sessions` | access 与 refresh 都绑定可撤销会话，撤销立即生效 |
| 密码 | bcrypt | 成熟的密码哈希格式 |
| API 文档 | 真实路由 + Go 类型 + kin-openapi 生成 | 路由、DTO、错误码和生成物都有双向覆盖/漂移检查 |
| 测试 | `testing`、testify、testcontainers-go | 并发、触发器、事务和 PostgreSQL 约束在真实数据库上验证 |
| 运行镜像 | 多阶段构建 + distroless nonroot | 静态二进制、无 shell、最小运行时攻击面 |

## 3. 进程与组件

仓库产出两个独立二进制：

| 二进制 | 生命周期 | 职责 |
|---|---|---|
| `danshi-server` | 常驻 | 校验配置、连接数据库、核对 schema 版本、装配 Hertz 路由并提供 HTTP 服务 |
| `danshi-migrate` | 一次性 | 在 PostgreSQL 上执行 goose `up`、单步 `down`、`status` 或 `version` |

迁移不嵌入 server 启动流程。部署编排必须先成功执行 migrate，再启动或滚动 server。这样多副本发布不会让每个服务副本争相修改 schema，迁移失败也不会产生部分新代码连接旧结构的状态。

SQL migrations 通过 `go:embed` 编入迁移二进制，因此运行镜像不需要携带额外 SQL 文件，也不存在镜像中 SQL 与构建时源码不同步的问题。

## 4. 分层与依赖方向

### 4.1 依赖图

```text
cmd/danshi-server
       │
       ▼
router ──► handler ──► service ──► repository ──► model
  │            │            │             │
  │            │            └─────────────┴──► infra ports/adapters
  │            └──► apierr / envelope
  └──► middleware / config / obs
```

`.golangci.yml` 的 `depguard` 强制以下规则：

- handler 不得导入 GORM，也不得直接调用 repository；
- service 不得依赖 Hertz；
- repository 不得依赖 handler 或 service；
- model 是叶子层，不反向依赖上层。

### 4.2 各层职责

#### Router

- 定义 `/api/v2` 路由组；
- 挂载认证、权限、UoW、错误恢复和请求 ID 中间件；
- 注册 `/health`、`/ready` 和 `/metrics` 等运行时端点；
- 组装 handler 依赖。

#### Handler

- 解析 path、query 和 JSON body；
- 执行输入形态与字段校验；
- 调用 service；
- 组装统一成功响应；
- 把错误交给唯一错误处理中间件。

Handler 不自行写业务错误响应，也不开始或提交事务。

#### Service

- 权限与资源可见性判断；
- 跨 repository 的业务编排；
- 事务内锁序和并发协议；
- 内容状态机、版本、审核、会话和外部服务流程；
- 把基础设施错误转换为稳定业务错误。

#### Repository

- 构造 GORM 查询；
- 预加载或批量加载关联，防止 N+1；
- 使用数据库约束和行锁；
- 不做 HTTP 或展示层判断。

#### Model

- 映射表和字段；
- 表达运行时读写权限，例如计数列只读；
- 不拥有 schema 创建权。

## 5. 事务模型

### 5.1 每请求一个事务

业务路由由 UoW 中间件包裹。成功响应提交，错误或 panic 回滚。repository 一律通过 `db.FromContext(ctx)` 取得当前事务句柄。

禁止把独立 `*gorm.DB` 注入 repository 方法。否则一个请求中的部分写入可能绕开 UoW 提前提交，产生“一半成功、一半回滚”的状态。

公开配置、探针和外部审核回调是否经过 UoW 由路由定义决定；`/health` 与 `/ready` 不进入业务事务。

### 5.2 提交后副作用与 durable outbox

数据库提交之前不应向不可回滚的外部系统宣告成功。需要在事务成功后执行的动作通过 after-commit 机制登记；事务回滚时不执行。

典型副作用包括发送通知、触发外部审核或上报告警。必须区分：

- 数据库状态是业务事实；
- 外部调用可能超时、失败或重试；
- 回调和重试入口必须幂等。

安全相关且要求最终收敛的副作用不能只依赖进程内 after-commit。图片审核终态会在同一事务追加 `image_access_intents`，并投影到每图片单例的 `image_access_deliveries`；后台 jobs 用 generation/lease fencing 始终执行 COS ACL，并只对可能已缓存过公开或私有响应的 URL 执行 EdgeOne purge。外部调用不持有数据库事务，进程崩溃由 lease 到期恢复，Create 响应未知先查询对账而不盲目重放。

## 6. HTTP 契约

### 6.1 路由与运行时端点

- 业务 API 前缀固定为 `/api/v2`。
- `/health`：进程存活，不访问数据库。
- `/ready`：检查数据库连通性；失败返回脱敏 503。
- `/metrics`：应用直出 Prometheus 文本格式指标，由 Prometheus 拉取；该端点不鉴权且不进入 UoW，抓取不会开启数据库事务。
- 尾部斜杠不依赖隐式重定向；未匹配路径返回统一 404。
- Hertz 开启 method-not-allowed 处理，方法不匹配返回统一 405。

### 6.2 统一响应信封

成功响应：

```json
{
  "code": 200,
  "message": "ok",
  "data": {}
}
```

业务错误：

```json
{
  "code": 403,
  "message": "账号已被封禁",
  "error_code": "account_banned",
  "data": null
}
```

`code` 等于 HTTP status。成功响应不含 `error_code`；所有非 2xx 业务响应都含稳定的 `error_code`。

500 响应的 `data.error_id` 与结构化日志关联。客户端只看到脱敏文案，不返回数据库错误、堆栈或敏感原因。

### 6.3 校验错误

422 使用字段级错误数组：

```json
{
  "code": 422,
  "message": "标题长度不能超过 200 个字符",
  "error_code": "validation_failed",
  "data": {
    "errors": [
      {
        "field": "title",
        "code": "too_long",
        "message": "标题长度不能超过 200 个字符"
      }
    ]
  }
}
```

- `field` 使用点号路径，例如 `budget_range.max` 和 `images.3`；
- `code` 是稳定机读枚举；
- `message` 是中文人类可读说明；
- 不回显被拒绝的原始敏感输入。

`internal/apierr/codes.go` 是字段错误码和业务错误码的唯一清单。业务代码不得散落字符串错误码。

### 6.4 401 与 403

返回 401 的情况包括：

- 缺少或无法解析 Bearer token；
- 签名、过期时间或 token 类型无效；
- `sub` 与 `sid` 不能对应有效用户会话；
- 会话已撤销或过期；
- 用户已注销或凭据指向的用户不存在。

返回 403 的情况包括：

- 已认证用户角色不足；
- 已认证用户处于封禁状态；
- 已认证用户无权操作指定资源。

所有 401 使用同一句脱敏文案，具体原因只写入内部日志。

### 6.5 稳定 wire 规则

- JSON 字段统一使用 `snake_case`。
- 时间转为 UTC；无微秒时省略小数，有微秒时固定六位，偏移写 `+00:00`。
- `price` 输入和输出均为十进制字符串，输出固定两位小数，可空值输出 `null`。
- ID 在 JSON 中是整数；可预见规模必须保持在 JavaScript 安全整数范围内。
- 分页严格校验 `page >= 1` 与 `1 <= limit <= 100`，不做隐式钳制。
- 搜索高亮先 HTML 转义源文本，再插入允许的 `<em>`；截断按 Unicode rune。

## 7. 配置模型

`internal/config` 的 `bindings` map 是环境变量的唯一清单。

加载流程：

1. 为每个 key 设置默认值；
2. 对每个环境变量显式调用 `BindEnv`；
3. 反序列化为 `Config` 值；
4. 一次性运行全部启动校验；
5. 把 `Config` 作为值注入各组件，后续不再读取全局 Viper。

不使用 `AutomaticEnv`，避免下划线、点号或前缀推导让真实变量名不透明。

启动校验一次收集所有问题，减少“修改一项、重启一次”的排障循环。主要校验包括：

- profile 和端口范围；
- PostgreSQL URL 形态、数据库名和 `TimeZone=UTC`；
- 连接池上下限；
- JWT 与验证码密钥长度和占位值黑名单；
- access 有效期短于 refresh 有效期；
- 邮箱域名白名单；
- CORS credentials 与 `*` 互斥；
- COS 大小与预签名 TTL 为正；
- 外部 URL 使用 HTTPS 且不含 URL userinfo；
- 生产环境的邮箱验证、CORS、云凭据、SES、COS 和审核回调配置完整。

完整变量表见根目录 [README](../README.md#配置)。

## 8. Schema ownership

### 8.1 单一真源

`migrations/*.sql` 是 schema 的唯一真源。GORM model 只负责运行时映射，不调用 AutoMigrate。测试、应用启动和测试夹具都不得另建第二套 schema。

所有迁移按 goose 版本顺序执行。`goose_db_version` 是运行版本真源；server 内嵌期望版本并在监听前做严格相等检查：

- 数据库版本偏低：说明迁移未完成；
- 数据库版本偏高：说明服务镜像过旧；
- 两种情况都拒绝启动。

详细决定见 [ADR 0001](adr/0001-schema-ownership.md)。

### 8.2 表分组

当前业务 schema 有 24 张表：

| 领域 | 表 |
|---|---|
| 封闭词表 | `canteens`、`canteen_windows`、`cuisines`、`flavors` |
| 开放标签 | `tags`、`post_tags` |
| 用户与认证 | `users`、`email_verification_codes`、`user_sessions` |
| 图片 | `image_assets`、`post_images` |
| 帖子 | `posts`、`post_flavors`、`favorites`、`post_likes` |
| 评论 | `comments`、`comment_mentions`、`comment_likes` |
| 社交与通知 | `follows`、`notifications` |
| 内容版本 | `post_histories`、`comment_histories` |
| 审核与提议 | `moderation_records`、`dictionary_suggestions` |

24 张表只是当前结构的核对值，不应在业务逻辑中硬编码。新增 migration 时同步更新 schema smoke 的结构断言。

## 9. 数据模型设计

### 9.1 主键与可枚举性

代理主键统一为：

```sql
bigint GENERATED BY DEFAULT AS IDENTITY
```

使用 `BY DEFAULT` 允许一次性数据导入显式指定 ID。显式装载后必须推进每张表的 sequence；空表要用 `is_called=false` 分支，保证下一个值仍为 1。

连续整数 ID 可枚举，因此所有按 ID 查询的接口都必须执行认证、资源可见性和所有权判断。草稿或待审内容不能依赖“ID 猜不到”获得保护。

### 9.2 规范化原则

可检索、可维护或需要引用完整性的多值数据使用关联表：

| 业务概念 | 结构 |
|---|---|
| 话题标签 | `tags` + `post_tags` |
| 口味与偏好 | `flavors` + `post_flavors(stance)` |
| 图片顺序 | `post_images(post_id, position, image_asset_id)` |
| 评论提及 | `comment_mentions(comment_id, user_id)` |
| 帖子与评论点赞 | 独立 `post_likes` / `comment_likes` |
| 通知目标 | `related_post_id` / `related_comment_id` 真外键 |
| 头像 | `users.avatar_image_asset_id` 真外键 |

`post_flavors.stance` 取 `has`、`prefer` 或 `avoid`。主键 `(post_id, flavor_id)` 防止同一提问帖把同一口味同时标记为偏好和避开；冗余 `post_type` 与帖子类型形成复合外键，数据库直接拒绝不合法立场。

预算拍平成 `budget_min` 与 `budget_max`，便于约束、筛选和索引。两列必须成对出现，且下限不能大于上限。

### 9.3 开放标签与封闭词表

`tags` 是用户开放创建的标签：

- 名称最长 10 字符；
- 数据库存储值必须去除首尾空白；
- 唯一索引按 `lower(name)` 判定；
- 应用写入前执行 NFKC 归一化；
- 标签可被审核下架，但关联行保留。

`flavors`、`cuisines`、`canteens` 和 `canteen_windows` 是封闭词表：

- 启用条目由 `/config` 下发；
- 停用条目不再供新内容选择，历史外键继续有效；
- 被帖子或审核历史引用的条目受 `RESTRICT` 保护，只能停用；
- 餐厅 `code` 是稳定对外标识，名称可以修改，code 不可修改。

### 9.4 餐厅与窗口

帖子地点由可空的餐厅和窗口组成：

```text
posts.canteen_id        → canteens.id
posts.canteen_window_id → canteen_windows.id
```

两个约束共同保证合法性：

1. CHECK：有窗口时必须有餐厅；
2. 复合外键：`(canteen_window_id, canteen_id)` 必须匹配同一个窗口及其所属餐厅。

窗口楼层是可空字符串而不是整数，以容纳 `B1`、夹层等表达。同餐厅、同楼层、同名窗口唯一；`NULLS NOT DISTINCT` 让“楼层未填”的同名窗口也参与判重。

`posts(canteen_window_id, created_at DESC)` 的部分索引为窗口聚合页预留，无需再改 schema。

### 9.5 评论回复链

评论同时保存：

- `parent_id`：直接被回复的评论；
- `root_id`：这一条回复所属的楼主评论；
- `reply_to_user_id`：被回复用户；
- `effective_root_id`：`COALESCE(root_id, id)` 的生成列。

复合外键把 `parent_id`、`post_id` 和 `root_id` 绑定到父评论，保证父子在同一帖子且归属同一楼。应用可以保留任意深度的真实回复链，读取时按 root 拍扁展示。

楼主评论的 `reply_count` 统计整个楼内未删除回复；回复行计数恒为 0。

### 9.6 通知目标

通知类型决定唯一合法目标：

| 类型 | 目标 | `content` |
|---|---|---|
| `like_post`、`comment` | 帖子 | 仅 `comment` 需要非空预览 |
| `like_comment`、`reply`、`mention` | 评论 | `reply`、`mention` 需要非空预览 |
| `follow` | 无 | 必须为空 |

数据库 CHECK 保证目标列数量、目标类型与 content 形态一致，避免多态裸 ID 和无意义字段组合。

## 10. 时间与计数器

### 10.1 `updated_at` 属于应用语义

Schema 不为 `updated_at` 设置通用触发器。该字段表示“内容被编辑”，而点赞、收藏、浏览或后台对账都不是内容编辑。

GORM 的 `autoUpdateTime` 负责正常内容更新。非内容变更必须绕过自动更新时间：

```go
tx.Model(&post).UpdateColumn("view_count", gorm.Expr("view_count + 1"))
```

不能用 `Update` 或 `Updates` 实现浏览数自增。

### 10.2 机械计数由数据库维护

以下字段是动作表的机械派生值：

- `posts.like_count`；
- `posts.favorite_count`；
- `posts.comment_count`；
- `comments.like_count`；
- `comments.reply_count`。

关联表 INSERT、DELETE 以及评论软删除/恢复触发器在同一事务同步计数。

`BEFORE UPDATE` 写保护禁止业务直接修改计数列。重算函数在事务内临时设置：

```sql
SET LOCAL danshi.allow_counter_write = 'on';
```

`danshi_recount_all()` 从动作表重算所有计数，并返回修正行数供测试和运维断言。

逃生阀是事务局部而不是函数局部。数据库函数必须保存并恢复进入函数前的设置，避免调用后同一事务的任意写入继续绕过保护。

## 11. 删除、历史与不可篡改

### 11.1 实体和动作的边界

有独立生命周期、需要恢复或审计的实体采用软删除：用户、帖子、评论、标签。数据库触发器直接拒绝这些表的普通 `DELETE`。管理员下架帖子写入 `deleted_reason=admin`，保留帖子与图片关联供取证；它不是机审误杀，现有恢复端点只接受 `deleted_reason=moderation`，不会恢复管理员主动下架的帖子。

点赞、收藏、关注、标签/口味/图片关联属于动作，取消时物理删除。否则复合主键会让“已取消”的软删除行永久占位，用户无法再次执行同一动作。

词表通常停用；图片资产使用 `retired` 状态。

### 11.2 运维硬删除通道

受控物理清理在同一事务中显式设置：

```sql
SET LOCAL danshi.allow_hard_delete = 'on';
```

该开关只绕过禁删触发器，不绕过外键 `RESTRICT`。因此它不是用户级合规清除器。完整用户清除需要先定义审计身份匿名化、内容范围、多个开关的顺序和对账日志。

### 11.3 被替换版本历史

`post_histories` 和 `comment_histories` 只保存被编辑替换掉的旧版本：

- 创建时不写历史，主表是当前内容的唯一真源；
- 首次编辑先把当时主表内容追加为 `revision=1`，再更新主表；
- 后续编辑在主体行锁内按 `max(history.revision)+1` 追加旧版本；
- 帖子快照覆盖主体字段和跨关联表的可编辑数据；
- 评论快照保存正文；
- 历史表禁止 UPDATE 和普通 DELETE；
- 主表不保存 revision，也不要求主表等于最新历史；
- 审核记录只关联内容对象和字段，不锚定历史行。

每次编辑都会重新送审并新增审核流水。旧的未处理 `review` 流水继续保留，但待复核查询只展示
同对象、同场景、同字段的最新机审，因此管理员不会裁决已经被替换的内容。

## 12. 服务层协议

数据库不能单独保证所有跨语句不变式。以下协议是 service 层的硬约束。

### 12.1 创建与编辑版本协议

创建帖子或评论时：

1. 校验输入与关联资源；
2. 插入主体；
3. 写入主体、关联和顺序信息；
4. 不写历史；
5. 创建归属于当前对象的审核任务或状态；
6. 在同一事务提交。

编辑时：

1. `SELECT ... FOR UPDATE` 锁定主体行；
2. 校验操作者与当前状态；
3. 读取当前主体及全部可编辑关联，构造将被替换的完整快照；
4. 在锁内以 `max(history.revision)+1` 分配历史 revision，首次编辑得到 1；
5. 先追加旧版本历史，再更新主体和全部关联；
6. 重置审核状态并创建归属于当前对象的新审核任务；
7. 不比较主表与最新历史是否相等；
8. 同一事务提交。

所有编辑入口必须遵循同一锁顺序。唯一约束冲突不能被吞掉；并发编辑要么在行锁后串行得到连续版本，要么按显式乐观锁语义返回冲突。

集成测试至少覆盖：

- 两个并发编辑得到连续 revision；
- 创建成功后历史表为空；
- 首次编辑得到一行 revision 1，内容是编辑前版本；
- 历史写入失败时主体回滚；
- 编辑重新送审后，旧待复核流水不再出现在队列；
- 人工复核只能 supersede 同一对象、同一字段的机审记录。

### 12.2 图片引用锁序

图片引用的触发器负责：

- 新增引用时把资产激活为 `ready`；
- 删除最后一个引用时把资产退役。

触发器无法单独解决“删除最后引用”和“并发新增引用”的快照竞态。因此所有会改变图片引用的路径都必须：

1. 汇总涉及的 `image_assets.id`；
2. 去重并按 ID 升序排序；
3. 依次 `SELECT ... FOR UPDATE` 锁定资产行；
4. 在持锁事务内增删 `post_images` 或修改头像绑定；
5. 提交后释放锁。

该协议适用于发帖、编辑帖子、删帖、恢复、头像换绑和任何批量清理路径。统一排序避免两个事务以相反顺序锁多张图片导致死锁。

并发测试必须断言：存在有效引用时资产不能最终处于 `retired`；无任何帖子或头像引用时资产可以退役。

### 12.3 计数器写保护协议

- 业务 repository 不接收任何计数列更新值；
- 新建主体计数必须为 0，INSERT 触发器会拒绝非零初值；
- 点赞、收藏、评论和软删除只操作源表或删除标记；
- 运维重算使用 `danshi_recount_all()`；
- ETL 推荐不写初始计数，让关联表触发器累加，最后执行 recount 并断言修正数为 0；
- 如果特殊脚本显式开启 `allow_counter_write`，事务边界必须独立且可审计。

### 12.4 会话协议

登录：

1. 验证邮箱、密码和用户封禁状态；
2. 插入 `user_sessions`，保存 refresh token 摘要、设备和有效期；
3. 为 access 与 refresh 签入相同 `sub` 和 `sid`；
4. 返回令牌。

鉴权：

1. 严格解析 Bearer token；
2. 验证签名、`exp` 和 token 类型；
3. 按 `sid + sub` 连接会话与用户；
4. 会话必须未撤销、未过期；
5. 用户必须未注销、未封禁；
6. 失败统一返回 401，角色或所有权不足在认证后返回 403。

刷新必须额外比对 refresh 摘要。登出更新 `revoked_at`，不删除会话行。登出全部设备和封禁用户都批量撤销该用户仍有效的会话。

### 12.5 图片与帖子发布协议

图片审核异步进行，因此允许帖子先引用审核中的图片。发布状态变化必须在事务内检查：

- 帖子自身内容审核通过；
- 所有引用图片都已审核通过；
- 当前对象最新一次文本审核通过；
- 帖子未被删除。

任一条件不满足时帖子不得进入 `approved`。把规则设计为“不得发布”而不是“不得引用”，避免用户提交表单时因异步图片审核尚未完成而丢失内容关系。

## 13. 审核状态机

### 13.1 对象状态

审核对象包括帖子、评论、标签、用户字段和图片。

机器 verdict：

- `pass`：通过；
- `review`：需要人工复核；
- `block`：违规。

帖子先审后发；评论先写入但只有 `pass` 才公开，作者始终可见自己的待审或违规原文；
标签和用户字段先发后审；图片上传完成后异步审核。

### 13.2 追加流水

`moderation_records` 一次审核一行。数据库强制：

- 一行只关联一种审核对象；
- 帖子/评论审核只关联内容对象，不关联历史版本；
- `(provider, provider_job_id)` 对非空外部任务号唯一；
- 机器记录不能带人工 reviewer；
- 人工记录必须带 reviewer 和 reviewed_at；
- 记录不可 UPDATE，普通 DELETE 也被拒绝。

人工复核不是修改机器记录，而是插入新行：

```text
机器记录 verdict=review
        ▲
        │ supersedes_id
人工记录 provider=manual, verdict=pass|block
```

触发器验证人工记录必须：

- 指向存在的非人工 `review` 记录；
- 与被复核记录属于同一对象和字段；
- 一条机审记录最多被复核一次。

待复核队列的定义是：机器 verdict 为 `review`，不存在任何人工记录 supersede 它，并且对
帖子或评论而言，同对象、同场景、同字段不存在更新的机审流水。旧记录不撤销、不标记，
只是从队列投影中排除。

### 13.3 对象处置

- 帖子：pass 可发布，review 留在待审，block 驳回；
- 评论：当前审核状态写回 `comments.moderation`；只有 `pass` 进入公开列表和计数，
  `review` 进入人工队列且仅作者可见，`block` 软删除并标记审核来源；
- 标签：block 下架，保留帖子关联；
- 用户字段：违规时通知管理员，由管理员重置或封禁；
- 图片：block 后不支持帖子进入公开状态；同事务写 durable 访问意图，后台 worker 把 COS ACL 收敛为私有并确认 EdgeOne 精确刷新终态，人工改判可恢复公开 ACL。
- 管理员下架帖子：按信息流/详情的同一公开口径（`deleted_at IS NULL AND status='approved'`）检查每张附图。仍被其他公开帖子引用的图片保持原状；已无公开帖子引用的图片在下架事务内追加 `provider=admin_post_delete`、`verdict=block`、带 reviewer 且无 `supersedes_id` 的独立流水，写回 `image_assets.moderation=block`，并写入 `desired_public=false`、`purge_required=true` 的访问意图。外部 COS/EdgeOne 调用仍只由事务外 worker 执行。

系统不根据单条机器 verdict 自动封禁用户。

## 14. 词条提议状态机

`dictionary_suggestions` 覆盖 `flavor`、`cuisine`、`canteen` 和 `canteen_window`。

状态只有：

```text
pending ──► approved
       └──► rejected
```

终态不可回到 pending。终态下提议内容、审核结论、结果条目和关系被冻结；来源帖子在受控物理清除时允许被 `SET NULL`，但不能改绑到另一帖子。

数据库约束保证：

- `flavor` 提议必须带 `flavor_stance`；
- 窗口提议必须关联既有餐厅或同批餐厅提议；
- pending 不带审核人、审核时间和产出；
- rejected 必须有驳回理由；
- approved 必须恰有一个与 kind 匹配的结果外键；
- 已批准结果被 `RESTRICT` 保护，不能抹掉审核历史；
- 父餐厅提议未批准时，子窗口提议不能批准；
- 批出的窗口必须确实属于父提议批出的餐厅。

批准 service 在单一事务中完成：创建或复用词条、写入审核字段、回填 `resulting_*_id`、按 kind 回绑来源帖子。任一步失败全部回滚。

刻意不设“同名 pending 唯一”约束。多个用户可能为不同帖子提议同一个词，管理员可以让这些提议分别保留审计记录并指向同一结果条目。

## 15. 图片资产

`image_assets.status`：

| 状态 | 语义 |
|---|---|
| `pending` | 尚无业务引用；对象可能仍在上传，也可能已完成并等待引用 |
| `ready` | 当前至少存在一条帖子或头像引用 |
| `retired` | 曾被引用后已解除全部引用，或无引用对象已清理；记录仍保留 |

对象是否完成校验由 `public_url` 是否仍为空表达，不与引用状态混用。建立帖子图片或
头像引用时由触发器激活为 `ready`；解除最后引用时由触发器退役。过期回收只领取
无引用的 `pending` 行，并在删除对象后用内部墓碑 URN 替换失效公开 URL。

图片行禁止普通物理删除。受控清除使用独立的 `danshi.allow_image_asset_delete` 事务开关或封装函数。

图片公开 URL 不在帖子里冗余存储；`post_images` 通过外键引用资产并用 `position` 保序。头像同样存资产 ID，而不是游离 URL。

完整客户端协议见[图片上传与资产生命周期](image-hosting.md)。

## 16. 数据库迁移与版本门禁

新增 migration 时：

1. 使用递增的五位版本号；
2. 同时实现 `Up` 与可演练的 `Down`；
3. 把新约束的正例、负例和可恢复行为加入 schema smoke；
4. 在两套独立干净数据库中分别验证 `up → smoke` 与 `up → down → up`；
5. 故意破坏一条断言，证明测试确实非零退出；
6. 更新 `ExpectedVersion` 及相关运行文档；
7. 部署时先运行 migrate，再启动 server。

两条 schema 链路必须隔离。数据 smoke 会有意留下受 `RESTRICT` 保护的记录，在同一库继续 down 可能正确失败；这不能被误判为迁移本身不可回滚。

一次性历史数据导入不属于常规 migration，单独见[历史数据迁入方案](history/data-migration-plan.md)。

## 17. OpenAPI 生成与门禁

`api/openapi.json` 是 OpenAPI 3.0.3 生成物。生成输入包括：

- Hertz 运行时路由表；
- `internal/apicontract` 的状态码和鉴权声明；
- handler 同包注册的真实请求 DTO 与 service 响应类型；
- `internal/apierr/codes.go` 的错误码 AST 解析结果；
- 对时间、金额、decimal 和 raw JSON 的显式 schema 定制。

生成前执行双向对账：

1. 运行时路由与 route/status/auth 注册表集合相等；
2. 运行时路由与请求/响应类型绑定集合相等；
3. 两类注册表内部无重复 method/path。

`make openapi-generate` 写入新文件；`make openapi` 在内存中重新生成并与已提交文件逐字节比较。新增路由、删除路由、漏类型、漏状态、错误码变化或生成物过期都会失败。

OpenAPI 的 wire 类型、枚举与 nullability来自 Go 类型和显式定制。跨字段业务条件仍由代码校验和契约测试保护，不在第二份手写 schema 中重复维护。

## 19. 容器与 CI

`deploy/docker/Dockerfile` 共享依赖和构建阶段，输出 server 与 migrate 两个 distroless/nonroot target。

构建设置：

- `CGO_ENABLED=0`；
- `-trimpath`；
- `-ldflags="-s -w"`；
- server 内嵌 `time/tzdata`，不依赖运行镜像时区包；
- migration SQL 编入二进制。

Compose 使用 `service_completed_successfully` 表达 migrate 必须先成功结束。PostgreSQL 与 server 的宿主机端口可通过 `DANSHI_POSTGRES_PORT` 和 `DANSHI_SERVER_PORT` 覆盖。

GitHub Actions 当前包含：

- lint：gofmt、OpenAPI 漂移与 golangci-lint；
- test：全包 race 测试；
- schema：两条独立 schema 回归链路；
- build：四个二进制、体积门禁和三个镜像构建；
- runtime：Compose 启动、探针和统一 404 响应验证。

二进制门禁当前为 server 不超过 32 MiB、migrate 不超过 15 MiB、jobs 不超过 40 MiB、
legacy-import 不超过 15 MiB。server 阈值包含 Prometheus client、OTel SDK 与 OTLP
exporter 的静态链接成本；jobs 包含数据库与腾讯云 COS 适配器，早期静态构建实测约
27 MiB，接入图片访问收敛 worker 后又静态链接了腾讯云 EdgeOne（`teo/v20220901`）
SDK，实测升到 33 MiB，因此阈值按实测重新基线到 40 MiB；migrate 与 legacy-import
都不依赖观测栈和云 SDK，实测约 10 MiB。阈值基于实际静态构建；超过阈值时应分析依赖
或明确调整文档和门禁，不应静默删除检查。

## 20. 可观测性现状

已经具备：

- `slog` 结构化日志；
- 开发环境人类可读文本，生产环境 JSON；
- 日志包含 service 和 profile，请求日志从 context 自动补充 `request_id`，启用 tracing 时同时补充 `trace_id` 与 `span_id`；
- 统一 500 `error_id`；
- 应用通过独立 Prometheus registry 在 `/metrics` 直出 HTTP、数据库连接池、审核、验证码、Go runtime 与进程指标；
- OTel trace provider 通过 OTLP/HTTP 推送到 `OTLP_ENDPOINT`，HTTP server span 使用路由模板命名；
- GORM 操作创建 DB client span，记录有限的 operation/table 属性，不记录 SQL 文本或变量值；
- 腾讯 COS、腾讯 CI、腾讯 SES 与飞书 webhook 的网络调用创建 external client span；名称和属性只使用
  固定的供应商与操作枚举，不记录对象键、邮箱、验证码、webhook URL、用户内容或供应商原始错误；
- `OTLP_ENDPOINT` 为空时不创建 exporter、provider、后台 processor、HTTP tracing 中间件或 DB tracing callback。

尚未完成：

- Collector、Prometheus、Tempo 或 Grafana 的仓库内部署配置。

指标与 trace 使用两条刻意独立的链路：指标始终由应用暴露、Prometheus 主动拉取，trace 才通过 OTLP 推送。Collector 不可用时不会影响 `/metrics` 抓取。仓库仍不提供空的 `deploy/otel` 或 `deploy/grafana` 目录；部署侧应连接现有可用的 Collector 和 Prometheus，而不是把占位配置误当成观测栈。

当前暴露的应用指标：

```text
danshi_http_server_requests_total{route,method,status}
danshi_http_server_request_duration_seconds{route,method,status}
danshi_http_server_response_size_bytes{route,method,status}
danshi_db_pool_connections{state}
danshi_db_pool_open_connections
danshi_db_pool_max_open_connections
danshi_db_pool_wait_total
danshi_db_pool_wait_duration_seconds_total
danshi_moderation_submissions_total{provider,scene}
danshi_moderation_provider_failures_total{provider,scene,reason}
danshi_moderation_terminal_outcomes_total{provider,scene,outcome}
danshi_moderation_callbacks_total{provider,outcome,reason}
danshi_moderation_review_queue_cached_items
danshi_moderation_review_queue_cache_ready
danshi_moderation_review_queue_last_success_timestamp_seconds
danshi_moderation_review_queue_last_refresh_success
danshi_moderation_review_queue_refresh_in_progress
danshi_moderation_review_queue_refresh_errors_total
danshi_verification_events_total{provider,outcome,reason}
go_*
process_*
```

`route` 只允许 Hertz 路由模板或固定值 `unmatched`，绝不回退到实际 path；`method` 只允许已知 HTTP 方法或 `OTHER`；`status` 只允许 100–599 或 `OTHER`；数据库 `state` 仅为 `in_use` / `idle`。业务指标的 `provider`、`scene`、`outcome`、`reason` 也全部在代码中收敛为固定枚举，未知值统一降为 `unknown`，不会透传用户、对象、任务、邮箱、正文或错误文本。

审核提交和供应商调用失败按真实调用即时计数。`pass`、`review`、`block` 与带 `provider_failed` 标签的失败终态，以及成功处理的回调和成功发信，只在当前 UoW 事务提交后计数；事务回滚不会制造业务成功。重复回调计入 `callbacks_total{outcome="processed",reason="duplicate"}`，但不会重复增加终态。

待复核队列不把无界 scrape 并发传给数据库。进程内 collector 以 15 秒为最小刷新间隔，并用 try-lock 语义保证同一时刻至多一个调用方执行查询；并发 scrape 立即返回最近成功缓存，不等待刷新。刷新复用应用连接池，在只读事务中执行，与管理端分页、积压告警使用完全相同的 `queue_items` 口径，并同时受 2.5 秒 PostgreSQL `statement_timeout` 和 3 秒调用 context 超时约束。collector 不启动后台 goroutine，也不创建独立连接池。

`review_queue_cached_items` 明确表示“最近一次成功观测值”，不能单独当作实时深度使用：告警必须同时查看 `cache_ready`、`last_refresh_success`、`refresh_in_progress`、`refresh_errors_total` 和 `last_success_timestamp_seconds`。启动尚无成功值或首次刷新失败时不导出 `cached_items`；已有缓存后的刷新失败会保留旧值，但失败状态和最后成功时间会明确暴露。刷新错误不会产生 invalid metric，也不会拖垮整个 `/metrics`。

DB trace 进一步省略整个 SQL 文本与变量值；外部调用 span 只使用 `external.system` 与 `external.operation` 两个固定枚举属性，失败只记录通用状态 `external call failed`，不记录供应商错误正文，防止邮箱、验证码、对象键、webhook token、用户内容或云端原始响应进入 telemetry。

## 21. 安全边界

- 生产密钥通过部署平台注入，不提交到 Git；
- JWT 与验证码密钥至少 32 字节并拒绝常见占位值；
- 生产 CORS 不允许通配来源；
- 图片 URL 与回调 URL 必须是 HTTPS；
- 数据库 URL 固定 UTC 语义；
- 认证失败脱敏；
- 资源 ID 可枚举，所有详情路由显式鉴权；
- 外部回调以 token、provider job ID 和幂等约束保护；
- 审核原始返回可保留，但日志、响应和 trace 不应泄露敏感内容；
- distroless 镜像以 nonroot 运行；
- schema 版本不匹配拒绝启动。

## 22. 已知边界

- 搜索包含前导通配时不能受普通 B-tree 索引帮助；数据规模扩大后应基于真实 EXPLAIN 决定 `pg_trgm` 或全文检索方案。
- 主键可枚举带来元数据暴露风险，必须持续依赖鉴权和可见性测试。
- refresh token 不轮转；泄露处置依赖会话列表和即时撤销。
- 仓库提供应用侧 `/metrics` 与 OTLP trace exporter，但不内置 Collector、Prometheus、Tempo 或 Grafana 部署栈。
- 用户级物理清除仍需单独的合规设计。
