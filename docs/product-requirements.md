## 1. 产品定位

旦食是面向复旦大学在校师生的校园美食分享平台。平台承载两类核心信息流：

- 已经吃过的用户分享体验，给出推荐或避雷意见；
- 有就餐问题的用户发起提问，包括菜品推荐、营业情况、排队情况和预算选择。

产品以移动端为主要入口，后端负责账号、校园餐饮词表、内容发布、互动、搜索、图片、审核和管理能力。

## 2. 术语

| 术语 | 实体 | 含义 |
|---|---|---|
| 用户 | `user` | 账号主体；注销采用软删除 |
| 会话 | `user_session` | 一台设备的一次登录，决定令牌是否仍有效 |
| 帖子 | `post` | 内容主体，分为分享帖和提问帖 |
| 分享帖 | `post_type=share` | 作者已经体验过，必须选择推荐或避雷 |
| 提问帖 | `post_type=seeking` | 与美食或就餐相关的问题 |
| 楼主评论 | root comment | 直接回复帖子的评论 |
| 楼 | thread | 一条楼主评论及其下所有回复 |
| 餐厅 | `canteen` | 帖子地点的一级维度，属于封闭词表 |
| 窗口 | `canteen_window` | 餐厅下的二级维度，可留空 |
| 口味 | `flavor` | 菜品风味或提问偏好，属于封闭词表 |
| 菜系 | `cuisine` | 菜品分类，属于封闭词表 |
| 话题标签 | `tag` | 用户自由创建的开放标签 |
| 词条提议 | `dictionary_suggestion` | 用户申请新增封闭词表内容的审核记录 |
| 图片资产 | `image_asset` | 对象存储中的图片及其归属、用途和生命周期记录 |
| 审核记录 | `moderation_record` | 一次机器或人工审核结论，只追加、不覆盖 |
| 软删除 | soft delete | 保留数据行并通过 `deleted_at` 标记不可见 |

## 3. 用户与权限

### 3.1 角色

一个用户可以绑定**多个角色**，有效能力是所有已绑定角色的能力**并集**。

| 角色 | 能力 |
|---|---|
| `user` | 浏览、发帖、评论、互动、提交词条提议 |
| `dict_reviewer` | 额外可审批词条提议、维护封闭词表（口味 / 菜系 / 餐厅 / 窗口） |
| `moderator` | 额外可审核帖子与评论、删除与恢复违规内容、处理人工复核队列、查看单个用户的完整历史（含未通过帖子与历史封禁记录）、封禁与解封 |
| `super_admin` | 拥有全部能力，额外可查看用户列表、调整用户角色、查看管理员名单 |

`moderator` **不具备**用户列表能力。封禁决策需要的是「这个人做过什么」的针对性取证，
而不是全站枚举加邮箱等个人信息；取证入口是单用户详情与其全部帖子（含未通过）。

鉴权中间件检查的是**能力**而不是角色，角色到能力的映射集中在一处，
因此权限模型演进不会波及端点与前端。

角色的授予与撤销、封禁与解封都**追加不可篡改的记录**，解封不会抹掉上一次的封禁理由。

权限不足时返回 403；身份缺失、令牌无效、会话失效或账号不存在时返回 401。401 不向客户端区分具体失败原因。

### 3.2 注册

注册流程为：填写邮箱 → 获取验证码 → 提交邮箱、验证码、密码、昵称和可选性别。

| 规则 | 要求 |
|---|---|
| 邮箱域名 | 只接受配置白名单中的域名；默认是 `fdueat.com`、`m.fudan.edu.cn` 和 `fudan.edu.cn` |
| 验证码 | 明文不落库，只保存摘要；有发送冷却、窗口限流和失败次数限制 |
| 防枚举 | 请求验证码时，不暴露邮箱是否已注册；已注册邮箱与可注册邮箱消耗相同的限流配额 |
| 密码 | 使用 bcrypt 保存；密码规则由 API 校验返回稳定字段错误码 |
| 昵称 | 非唯一，最长 100 字符；未设置时为空字符串 |
| 性别 | 可空；支持 `male`、`female` 和 `other` |
| 头像 | 注册时不能设置；登录后通过标准图片上传流程绑定本人头像资产 |

邮箱域名只在新注册时校验，登录不重复应用域名限制。

### 3.3 登录、刷新与会话

- 登录凭据为邮箱和密码。
- 登录成功签发 access token 与 refresh token，两者携带同一会话 ID。
- access token 默认有效 60 分钟；refresh token 与会话默认有效 30 天。
- refresh token 不轮转；撤销会话是令牌失效的安全机制。
- 每次鉴权都验证签名、令牌类型、用户 ID、会话 ID、会话未撤销且未过期，以及用户未注销、未封禁。
- 会话绝对过期，不因活跃而顺延。
- `last_seen_at` 节流更新，不能让每个鉴权请求都产生数据库写入。

用户可以：

- 撤销当前会话；
- 撤销全部会话；
- 查看自己的设备会话列表；
- 踢掉属于自己的指定会话。

撤销立即影响 access token 和 refresh token。撤销后的会话记录保留，用于安全审计。

### 3.4 封禁与注销

封禁支持限时和永久两种互斥形态。封禁理由必填；新封禁记录应保存执行管理员。封禁时撤销用户全部会话，封禁期间不能登录，但已公开内容仍可浏览。

限时封禁到期后按查询条件自动视为解除，不依赖定时任务。管理员主动解封时清理当前封禁标记、到期时间、理由和执行人。

用户注销采用软删除。注销后不能登录、不能出现在搜索或用户列表中；已发布内容保留，作者以已注销状态展示。

## 4. 用户资料与社交关系

用户资料包含昵称、头像、简介、性别和统计数据。邮箱与角色不在公开资料中返回。

- 用户可在同一资料更新接口修改昵称、简介、性别和头像。
- 头像只能绑定本人上传、用途为 `avatar`、已完成上传且审核为 `pass` 的图片资产；
  `pending/review` 图片暂不可绑定，当前头像保持不变。
- 换绑头像后，无其他引用的旧资产自动退役。
- 关注是单向关系；不能关注自己。
- 关注与取关必须幂等。
- 关注列表和粉丝列表分页返回。

## 5. 内容发布

### 5.1 帖子类型

| 字段 | 分享帖 `share` | 提问帖 `seeking` |
|---|---|---|
| 语义 | 分享已经体验过的菜品或餐厅 | 提出与美食、就餐有关的问题 |
| 子类型 | 必填：`recommend` 或 `warning` | 不适用 |
| 价格 | 可填写人均价格 | 不适用 |
| 预算 | 不适用 | 可填写最小值与最大值，必须成对出现且最小值不大于最大值 |
| 口味 | `has`，描述实际口味 | `prefer` 与 `avoid`，表达偏好和忌口 |

帖子还包含 `category`，用于区分食堂菜品和自制菜谱；该维度与帖子类型正交。

价格在 API 中使用十进制字符串，数据库使用 `NUMERIC(10,2)`，不经过二进制浮点数。

### 5.2 地点

帖子可以不选择地点，也可以选择餐厅，并进一步选择该餐厅下的窗口。

- 填写窗口时必须同时填写餐厅。
- 窗口必须属于所选餐厅。
- 餐厅通过稳定 `code` 对外暴露；改名不改变 code。
- 窗口可带可空的楼层字符串，以容纳 `1F`、`B1` 等表示。
- 历史帖子可以继续引用已停用的餐厅或窗口。

### 5.3 话题标签

话题标签是开放集合，允许用户在发帖时创建。

| 规则 | 要求 |
|---|---|
| 长度 | 单个标签最多 10 个字符 |
| 数量 | 单帖最多 10 个 |
| 规范化 | 写入前 trim 并做 Unicode NFKC 归一化 |
| 唯一性 | 大小写不敏感，展示保留首次创建的原文 |
| 审核 | 先发后审；违规标签下架，但帖子关联保留以便恢复 |
| 删除 | 仅软删除或合并，不走日常物理删除 |

标签支持帖子筛选、重命名、合并和实时热门统计。

### 5.4 封闭词表

口味、菜系、餐厅和窗口由后端维护，前端只能从 `/api/v2/config` 返回的启用条目中选择。

词条有三种运营语义：

- 启用：可被新内容选择；
- 停用：不再出现在选择列表中，但历史引用有效；
- 删除：仅允许删除从未被引用且没有审核历史的条目。

用户找不到合适词条时可以提交提议。提议可携带来源帖子；审批通过后创建或复用字典条目，并在同一事务中回绑来源帖子。驳回必须附理由。

餐厅与窗口可以成组提议。窗口提议引用同批餐厅提议时，管理员必须先批准餐厅，再批准窗口。多个用户可以为各自帖子提议同名词条，审核时允许它们指向同一个结果条目。

### 5.5 图片

- 单帖最多 9 张图片，顺序稳定。
- 帖子只能引用作者本人上传、用途为 `post` 的图片。
- 客户端按 `presign → PUT COS → complete` 的流程上传。
- `complete` 之前的资产不能作为可用图片返回。
- 图片上传完成后异步审核。
- 审核进行中允许建立帖子引用，但引用未通过图片的帖子不能进入公开状态。

详细协议见[图片上传与资产生命周期](image-hosting.md)。

#### 图片分级与缩略图（新增）

信息流一屏十余张图，直出原图对移动端流量与首屏时间都不可接受。
图片按用途分三档，由同一个对象存储文件派生：

| 档位 | 用途 | 处理参数 | 实测大小 |
|---|---|---|---|
| `thumb` | 信息流卡片 | `imageMogr2/thumbnail/720x720>/format/webp/quality/80` | 48 KB（原图 2.6%） |
| `display` | 帖子详情默认展示 | `imageMogr2/thumbnail/1440x1440>/format/webp/quality/85` | 137 KB（原图 7.4%） |
| `raw` | 点击查看大图、保存 | 无参数 | 1.75 MB |

实测样本为一张 1.75 MB 的手机照片。`720x720>` 的语义是**等比缩放使其装入 720×720 的框**，
即长边压到 720、保持原始长宽比；`>` 表示**只缩不放**，本来就小于该尺寸的图原样返回，
不产生处理费用。

**缩略图不落盘。** 由数据万象实时处理、CDN 边缘缓存。同一对象的不同处理参数各自独立缓存，
互不覆盖；同一张图的同一种处理只回源计费一次。因此不需要为缩略图新增存储记录、状态字段
或清理任务，原图删除后派生图自然消失。

**前端负责切换**：列表用 `thumb`，进入详情用 `display`，用户点击放大或保存时才请求 `raw`。

#### 三档图片字段（**新增**，非破坏）

响应中新增两个与 `images` **同序等长**的字符串数组：

```json
{
  "images":         ["https://img.fdueat.com/<key>"],
  "image_displays": ["https://img.fdueat.com/<key>?imageMogr2/thumbnail/1440x1440>/format/webp/quality/85"],
  "image_thumbs":   ["https://img.fdueat.com/<key>?imageMogr2/thumbnail/720x720>/format/webp/quality/80"]
}
```

`PostListItem` 与 `PostDetail` 使用同一结构，列表页**保留完整三档**不做裁剪，
以便前端从列表进入详情时可以先用已有链接占位。头像同理新增 `avatar_thumb_url`。

**`images` 的语义逐字不变**——它仍然是原图 URL 数组，仍然是图片资产的对外身份，
请求体与响应体含义一致：发帖与编辑时客户端提交 `images`，服务端据此反查资产。
派生档位只出现在响应中，不参与身份判定。

因此本项是附加式变更，老客户端无感知，不计入破坏性清单。

### 5.6 草稿与发布状态

| 状态 | 可见性与语义 |
|---|---|
| `draft` | 仅作者可见；允许暂时缺少发布必填字段 |
| `pending` | 已提交，等待机器或人工审核 |
| `approved` | 审核通过，公开可见 |
| `rejected` | 审核驳回，作者可查看状态 |

帖子采用先审后发。每次编辑后回到需要审核的状态。

## 6. 浏览与互动

- 信息流按时间倒序分页，可按帖子类型、分类、餐厅、菜系、口味和标签筛选。
- 所有分页参数严格校验：`page >= 1`，`1 <= limit <= 100`；非法值返回 422，不做静默钳制。
- 查看帖子详情会增加浏览数，但不会更新内容的 `updated_at`。
- 点赞、取消点赞、收藏和取消收藏必须幂等。
- 点赞数、收藏数、评论数和回复数必须与动作表真实行数一致。
- 收藏是私有书签；用户只能查看自己的收藏列表。

## 7. 评论

### 7.1 回复关系

| 用户动作 | 结构 |
|---|---|
| 直接评论帖子 | 新建楼主评论；回复目标是帖子作者 |
| 回复楼主评论 | `parent_id` 和 `root_id` 指向楼主评论 |
| 回复楼内回复 | `parent_id` 指向被回复评论，`root_id` 继续指向同一楼主评论 |

存储保留任意深度的真实回复链，展示按 `root_id` 拍扁为楼主评论和楼内回复两层。回复必须与父评论属于同一帖子。

楼主评论上的 `reply_count` 统计整层楼的有效回复数；回复行自身的 `reply_count` 恒为 0。

### 7.2 编辑与删除

评论可编辑。首次创建和每次编辑后的内容都形成连续 revision；当前评论内容必须等于最新 revision。编辑后重新送审。

评论删除采用软删除：

- 保留原文和回复链；
- 客户端展示“该评论已删除”占位；
- 子回复继续可见；
- 删除的评论不计入帖子评论数和楼层回复数；
- 删除来源区分作者、管理员和审核；
- 管理员可以恢复误杀内容，计数随恢复回补。

## 8. 内容版本与删除

### 8.1 全量版本

帖子与评论的每一个版本都保留，包括首次创建的 `revision 1`。版本记录包含版本号、修改人和修改时间。

- 主体记录始终等于最新版本。
- revision 对同一对象连续递增，不重复、不跳号。
- 审核记录必须指向明确版本。
- 客户端对编辑过的内容展示“已编辑”。

### 8.2 软删除边界

| 对象 | 删除方式 |
|---|---|
| 用户、帖子、评论、标签 | 软删除，保留审计和恢复能力 |
| 餐厅、窗口、菜系、口味 | 优先停用；受引用或审核历史约束时禁止删除 |
| 图片资产 | 退役，数据行保留 |
| 点赞、收藏、关注和关联行 | 物理删除，因为它们是可重复发生的动作 |
| 版本历史、审核流水 | 只追加，禁止修改和日常删除 |

物理清理内容实体只属于受控运维通道。运维开关不能绕过外键 `RESTRICT`；用户级合规清除需要独立设计匿名化、清除范围、顺序、对账和审计流程。

## 9. 通知

| 类型 | 触发 | 关联对象 | 正文预览 |
|---|---|---|---|
| `like_post` | 帖子被点赞 | 帖子 | 无 |
| `like_comment` | 评论被点赞 | 评论 | 无 |
| `comment` | 帖子收到楼主评论 | 帖子 | 评论正文前 100 字 |
| `reply` | 评论收到回复 | 评论 | 回复正文前 100 字 |
| `mention` | 评论提及用户 | 评论 | 评论正文前 100 字 |
| `follow` | 用户被关注 | 无 | 无 |

通知提供分页列表、按类型筛选、未读数、单条已读和全部已读。通知的关联目标与类型必须一致。

## 10. 搜索

- 帖子搜索覆盖标题和正文，并可叠加餐厅、菜系、口味等筛选。
- 用户搜索按昵称匹配。
- 结果高亮前必须转义源文本，防止用户内容注入 HTML。
- 文本截断按 Unicode 字符处理，不能按 UTF-8 字节截断。

## 11. 内容审核

### 11.1 审核范围

| 对象 | 内容 |
|---|---|
| 帖子 | 标题与正文 |
| 评论 | 正文 |
| 话题标签 | 标签名 |
| 用户 | 昵称与简介 |
| 图片 | 帖子图片与头像 |

封闭词表不走机器审核；新词条在提议流程中由管理员审核。

### 11.2 内容策略

平台只允许美食和就餐相关内容。违法、涉政、色情、广告等内容应阻断；主题相关性不明确的内容进入人工复核。系统不因单条机审结论自动封禁作者，封禁由管理员决策。

### 11.3 时序与处置

| 对象 | 时序 | 通过 | 需复核 | 违规 |
|---|---|---|---|---|
| 帖子 | 先审后发 | 公开 | 保持待审 | 驳回 |
| 评论 | 先发后审 | 保持可见 | 进入人工队列 | 软删除 |
| 标签 | 先发后审 | 保持可用 | 进入人工队列 | 下架 |
| 昵称、简介 | 先发后审 | 保持 | 进入人工队列 | 通知管理员处置 |
| 图片 | 上传完成后异步审核 | 可支持帖子发布 | 进入人工队列 | 不允许帖子发布 |

### 11.4 审核流水

- 每次机器审核写入独立记录。
- 外部回调按 `(provider, provider_job_id)` 幂等。
- 审核记录包括对象、字段、版本、供应商、外部任务号、结论、标签、分数和原始返回。
- 人工复核新增 `provider=manual` 的记录，通过 `supersedes_id` 指向被复核的机审 `review` 记录。
- 人工记录必须针对同一对象、同一字段和同一版本。
- 一条机审记录最多被人工复核一次。
- 审核记录不可覆盖修改或日常删除。

违规或需要人工介入的事件可以通过飞书 webhook 告警；告警通道和审核供应商均通过接口隔离。

## 12. 管理端

管理员能力包括：

- 查看与裁决待审帖子；
- 查看全部帖子和评论，执行软删除或恢复；
- 查看机器审核待复核队列并追加人工结论；
- 创建、修改、停用和受限删除封闭词表；
- 批准或驳回用户词条提议。

超级管理员额外可以：

- 查看用户列表；
- 设置限时或永久封禁并撤销全部会话；
- 解封用户；
- 调整用户角色；
- 查看管理员和超级管理员列表。

## 13. 非功能要求

### 13.1 数据一致性

- 一个业务请求在一个事务中提交或回滚。
- 计数器与动作表保持同事务一致，并能通过 `danshi_recount_all()` 对账。
- 图片、评论父链、提及用户、通知目标和词表引用均有外键或等价数据库约束。
- `updated_at` 只表示内容编辑；浏览和计数同步不改变它。
- 内容版本、审核版本和当前主体互相可追溯。
- 删除任何一条评论不得删除其他用户的回复。

### 13.2 安全

- 所有按连续整数 ID 查询资源的接口都进行鉴权与可见性判断，不能把“ID 难猜”当作防线。
- 只能引用本人上传且用途匹配的图片。
- 生产环境要求强密钥、显式 CORS 来源、邮箱验证、腾讯云、COS 和审核回调配置完整。
- 验证码、认证失败和数据库错误不向客户端泄露敏感细节。
- 封禁和会话撤销立即生效。
- 搜索高亮对用户内容转义。

### 13.3 API 契约

- 业务路由前缀为 `/api/v2`。
- 成功与错误响应都使用统一信封 `{code, message, data}`；错误响应额外包含稳定 `error_code`。
- 校验失败使用 422 和字段级错误数组，字段路径采用点号形式。
- 时间统一使用 UTC ISO 8601，偏移写作 `+00:00`；有微秒时固定六位。
- JSON 字段使用 `snake_case`。
- 精确契约由代码生成的 OpenAPI 和 HTTP 黑盒测试保护。

### 13.4 运行与测试

- `/health` 只报告进程存活，不访问数据库。
- `/ready` 验证数据库连通性，失败返回脱敏 503。
- 服务启动时校验数据库迁移版本，不匹配则拒绝启动。
- Schema 变更必须通过空库迁移、回滚、约束 smoke 和断言可失败性测试。
- 热路径查询数不随分页大小增长，避免 N+1。
- 生产环境不得写入冒烟测试数据；测试使用隔离数据库。

## 14. 暂不覆盖

- 独立的“某窗口下全部帖子”聚合页面；schema 已保留窗口索引。
- 口味词表分类学重整。
- 用户级合规物理清除流程。
- 产品埋点和行为分析。
- 审核阈值、违规标签映射和审核时延 SLO 的最终运营口径。
