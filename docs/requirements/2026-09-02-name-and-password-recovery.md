# name 身份化与密码找回需求（草案）

> 日期：2026-09-02
>
> 状态：待评审
>
> 本文记录 `name` 身份化与密码找回能力的新增需求。在评审通过并同步至产品 PRD 前，
> 不替代 `docs/product-requirements.md` 中的已生效产品规则。

## 1. 背景与目标

当前账号以邮箱作为登录凭据，`users.name` 是非唯一、可为空的展示昵称。产品需要将
`name` 作为用户在旦食全平台的公开身份标识，并允许用户使用 `name` 登录；同时，用户应能
通过绑定邮箱安全地重置遗忘的密码。

本需求的目标是：

- 一名用户有且仅有一个 `name`；
- `name` 在全平台唯一，可用于公开展示、搜索、提及等既有用户身份展示场景；
- 用户可使用绑定邮箱或 `name` 加密码登录；
- 用户遗忘密码时，可通过绑定邮箱完成密码重置；
- 账号身份、会话撤销和用户内容的既有安全语义不被削弱。

## 2. 术语

| 术语 | 含义 |
|---|---|
| name | 用户对外公开展示的、全平台唯一的身份标识；由现有 `users.name` 字段承载，不新增第二个字段。接口字段也使用 `name`。 |
| 绑定邮箱 | 用户注册时绑定到账号的邮箱；用于注册验证、登录和密码找回。 |
| 昵称 / 显示名 | `name` 的产品展示含义；不是第二个字段，也不是另一种账号标识。 |
| 密码重置 | 用户通过绑定邮箱验证码设置新密码的匿名流程，不要求已有登录态。 |

## 3. name 身份标识

`name` 采用社交产品中公开 handle 的语义：它是账号可见、可搜索、可登录的稳定标识，
不是可任意重复的个人简介字段。由于本产品不另设显示昵称，`name` 也直接展示在资料、
帖子和评论作者位置。

### 3.1 注册

- 注册时 `name` 为必填字段。
- `name` 写入现有 `users.name`，不新增任何身份字段。
- `name` 长度为 2–24 个 Unicode 字符，可使用中文、其他文字、数字和下划线；首尾不得为空白，
  不允许控制字符、表情符号、标点符号或连续空白。
- 写入前去除首尾空白并进行 Unicode NFKC 规范化；唯一性比较不区分大小写。因此 `Alice` 与
  `alice` 是同一个 name，但成功注册时保留用户提交的规范化展示大小写。
- 系统保留名称不得注册，包括 `admin`、`administrator`、`official`、`support`、`system`、
  `security`、`danshi` 及其以这些名称加下划线或数字形成的变体。保留清单由服务端维护，
  不向客户端暴露其完整内容。
- 注册成功后，`name` 与邮箱共同属于该账号：邮箱是私密的认证与找回凭据，`name` 是公开身份标识。

### 3.2 展示与既有能力

- 公开用户资料、帖子作者、评论作者、关注列表、搜索结果和管理端用户视图继续展示
  `users.name`，对外字段名保持 `name`。
- `name` 同时接受既有昵称内容审核；审核不通过的候选 name 不得写入账号。
- 用户注销后，其 `name` 永久保留，不被其他账号复用，以避免历史内容作者身份被错误归属。

### 3.3 登录

- 用户可使用“绑定邮箱 + 密码”或“`name` + 密码”登录。
- 两种方式在成功后签发相同的 access token、refresh token 和设备会话，不产生两套账号或会话语义。
- `name` 不存在、邮箱不存在、密码错误、账号已注销等认证失败情形不得向客户端暴露差异化信息。
- 封禁账号仍不得登录，沿用现有封禁与会话规则。

### 3.4 name 修改与存量账号

- 用户可以修改 `name`，但两次成功修改之间至少间隔 30 天；首次设置 `name` 不受该间隔限制。
- 修改前必须处于有效登录态并提交当前密码确认；修改后的 `name` 立即用于所有公开展示、搜索和
  后续登录。
- 旧 `name` 永久保留，不会立即或定期释放给其他账号。这避免改名后他人冒用旧身份、接收
  本应指向原作者的搜索与提及。
- name 修改属于账号资料变更，应保留“修改前 / 修改后 / 时间”的不可篡改审计记录；
  该记录仅向本人和有用户管理能力的管理员开放。
- 当前已有用户须在迁移窗口内补设符合规则的唯一 `name`；在补设前，存量账号仍可用邮箱登录，
  但不可使用 name 登录。迁移窗口结束后，未完成补设的账号不得继续登录，直至完成 name 设置。
- 重名或不符合新格式的历史 `name` 不自动生成替代值，避免系统替用户创建难以识别的公开身份；
  迁移窗口内由用户自行选择，冲突按先成功保存者取得。

## 4. 忘记密码与密码重置

### 4.1 发起重置

- 用户提交绑定邮箱以请求密码重置验证码。
- 服务端仅向可重置的已存在账号发送真实验证码。
- 无论邮箱不存在、账号已注销、账号不可重置或可正常重置，客户端均收到相同的成功响应，
  不得借此枚举账号状态。
- 验证码明文不得入库；发送冷却、窗口限流、过期时间、失败次数上限和一次性消费规则应与
  现有邮箱验证码安全策略一致。
- 密码重置验证码必须与注册验证码在用途上隔离，不能互相验证或互相覆盖。
- 每封邮件只包含一个 6 位数字验证码、有效期和“非本人操作请忽略”的安全提示；邮件不得
  包含密码、访问令牌或可直接登录的链接。

### 4.2 提交新密码

- 用户提交绑定邮箱、密码重置验证码和新密码以完成重置。
- 新密码必须满足与注册密码相同的密码规则，并以 bcrypt 保存。
- 验证码只能成功使用一次；过期、错误、已使用或尝试次数超限时不得重置密码。
- 密码更新与撤销该用户全部有效会话必须是同一原子操作。
- 重置成功后不自动创建登录会话；用户需使用新密码重新登录。
- 重置流程不得改变 `name`、绑定邮箱、角色、封禁状态、内容、关注关系或其他用户资料。

### 4.3 邮件与可用性

- 密码重置邮件必须明确说明其用途，不能沿用“注册验证码”的误导性主题或正文。
- 建议主题为“旦食密码重置验证码”；正文展示验证码、10 分钟有效期以及非本人操作提示。
- 生产环境未配置可用邮件投递能力时，重置请求应明确失败，不得伪造发送成功。
- 邮件、日志、指标、链路追踪和错误响应不得记录密码、验证码或完整的敏感邮件内容。

## 5. 验收标准

1. 新注册用户缺少 `name`、`name` 不符合格式或 `name` 冲突时，注册失败且不创建账号。
2. `Alice` 与 `alice` 只能注册其中一个；成功值保留提交时的规范化展示大小写。
3. 用户可分别通过正确的绑定邮箱和正确的 `name` 登录同一账号；两种登录都遵循相同的封禁、注销和会话规则。
4. 任一失败登录响应不泄露 `name` 或邮箱是否存在。
5. 请求密码重置不会通过响应体、状态码或发送配额差异泄露邮箱是否绑定账号。
6. 注册验证码不能用于重置密码，重置验证码也不能用于注册。
7. 重置成功后，重置前签发的 access token 与 refresh token 均立即失效。
8. 同一重置验证码不能重复使用；并发提交时至多一次成功。
9. 密码重置成功不会修改除密码哈希和会话撤销状态外的账号数据。
10. 用户修改 name 后，旧 name 不可被其他账号注册；30 天内不得再次修改。

## 6. 非目标

- 不新增独立的身份字段；
- 不改变用户主键、内容作者引用或角色模型；
- 不提供通过 `name` 找回密码的能力；
- 不在本需求中定义邮箱换绑、第三方登录、短信找回或多因素认证；
- 不提供旧 name 的自动转发、别名解析或历史 name 公开查询；
- 不在本需求中定义邮箱换绑后的二次验证细节。

## 8. 设计依据

- 公开名称采用“唯一、可搜索、可登录、与邮箱分离”的 handle 模式；X 将 handle 定义为唯一、
  出现在资料 URL、用于登录并可被搜索的账号标识。[X 帮助中心](https://help.x.com/en/managing-your-account/change-x-handle)
- `name` 允许修改但保留明确间隔，并要求当前密码确认，以降低被盗登录态直接改写公开身份的风险；
  Facebook 的名称修改也采用时间间隔与密码确认。[Facebook 帮助中心](https://www.facebook.com/help/173909489329079?locale=bg_BG)
- 密码找回使用发送到绑定邮箱的一次性验证码，不在邮件中发送密码或登录链接；
  这与主流账户恢复的邮箱验证码方式一致。[Google Account Help](https://support.google.com/accounts/answer/27445?hl=en)
