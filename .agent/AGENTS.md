# AGENTS.md

本文件是本仓库对 AI 编码代理与人类贡献者的共同约定。**任何代码、数据库 schema、HTTP
契约、配置或测试修改前，必须完整阅读本文件。**改动本文件前也先读完，
它只写「目标、第一性原理、Git 规范」三件事，其余细节在 `docs/` 与 `README.md`。

## 项目目标

旦食后端是复旦校园美食分享平台的服务端，为移动端提供账号与会话、校园餐厅与窗口词表、
帖子、评论、搜索、互动、图片直传、内容审核与管理端 API。

技术栈：Go + CloudWeGo Hertz + GORM + PostgreSQL 18，HTTP API 挂在 `/api/v2`。

服务的成功标准按重要性排序：

1. **数据不出错** —— 计数准确、引用完整、审核与编辑留痕可追溯
2. **不出安全事故** —— 权限边界清晰、用户内容不外泄、错误响应不泄露内部信息
3. **并发下稳定** —— 高并发写入不产生重复、跳号或状态不一致
4. **易于演进** —— 契约可生成、变更有门禁、改动有测试兜底

性能重要，但排在上面四条之后。

## 第一性原理

这些是本项目反复回到的判断依据。与它们冲突的方案，即使更省事也不采用。

### 数据库是约束的最终防线，应用层是唯一的业务真源

能用约束、外键、触发器表达的不变量就交给数据库强制（计数器写保护、禁止物理删除、
审核流水不可篡改、复合外键锚定版本）。但业务语义只在应用层：
`updated_at` 由业务逻辑维护而非触发器，因为只有应用知道哪次写入算「内容变更」。

### 软删除的边界是「实体」还是「动作」，不是「重要」还是「不重要」

有独立生命周期、需要恢复或审计的实体一律软删除，正常业务路径禁止物理删除。
纯关联表与动作表（点赞、收藏、关注、帖子↔标签/口味/图片）物理增删，
取消后必须能再次创建，唯一约束、幂等、级联与计数器都要正确。
审核流水与编辑历史按追加不可篡改处理。

### 契约从代码生成，不手写、不靠注释

`api/openapi.json` 由运行时路由表 + Go 类型生成。四道门禁保证它不腐烂：
路由覆盖、spec 漂移、错误码同步、GET 端点必须声明 query 参数。
注释会说谎而编译器不会——因此错误码、DTO、参数一律用类型表达，不用魔法注释。

### 一份看起来存在但不可信的产物，比没有更危险

半覆盖的 spec、只测 happy path 的测试、恒真的断言、空壳的监控配置，
都会让人以为某件事已经做到。宁可明确缺失，也不要虚假的完备。

### 不发明没人要求的规则

需求、约束与策略只记录和实施已经决定的内容。对未来阶段的推测不写进决策表，
也不写成 CHECK 约束。当一个约束开始逼出别扭的绕行方案时，
先问它是不是根本不该存在。

### 失败要显式，降级要有声

外部依赖不可用时 fail-closed，不伪造成功（未配置的发信与审核供应商返回 503，
不静默放行）。告警失败只记日志、不影响主事务，但绝不能悄悄丢掉。

### 权限检查能力，不检查角色

中间件判断的是「能不能做这件事」，不是「是不是某个角色」。
角色到能力的映射集中在一处，这样权限模型演进不会波及端点与前端。

## Git 规范

提交信息遵循 [Conventional Commits](https://www.conventionalcommits.org/)。

```
<type>(<scope>): <subject>

[optional body]

[optional footer]
```

### type

| type | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修缺陷 |
| `docs` | 只改文档 |
| `test` | 只改测试 |
| `refactor` | 重构，不改外部行为 |
| `perf` | 性能改动 |
| `build` | 构建、依赖、工具链 |
| `ci` | CI 配置 |
| `chore` | 其余杂项 |

破坏性变更在 type 后加 `!`，并在 footer 写 `BREAKING CHANGE: <说明>`。

### scope

用领域或包名：`auth` `post` `comment` `user` `notification` `search` `config`
`dictionary` `moderation` `upload` `admin` `apierr` `openapi` `schema` `deploy` 等。
跨多个域时省略 scope。

### subject

- 中文或英文均可，一行写完，**不加句号**
- 用祈使语气描述这次改动做了什么，不是描述现状
- 控制在 50 字符左右，硬上限 72

### body

**可选，且要克制。** 只写「为什么这么改」，不写「怎么验证的」「根因分析」「测试结果」——
那些属于 PR 描述、设计文档或 `.codex/reports/`，不属于每一条提交。
需要长篇解释时，说明这次提交可能太大，应该拆开。

### 其它

- 一次提交只做一件事，宁可多提几次
- 由 AI 代理产出的提交在 footer 保留 `Co-Authored-By`
